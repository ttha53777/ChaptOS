Ask Chapt · the row list

A list that knows what it's a list of.

Today, any answer that is “several things” gets the same stack of boxes. Compare, place in time, count, look up one thing: the reader does that work by reading every row. Here the rows are the same rows, but when they all share something, Ask Chapt draws that thing. Flip Today / New on any answer below to see the same rows both ways. Every other answer type is untouched.

01

Standings

When every row carries a number in the same unit, the question is really “how do they compare?” The numbers become bars on one scale, your own threshold is drawn through all of them, and the rows that miss it sit under a cut line. If the rows are dated things, like meetings, they keep their date order and nobody is ranked; the number is still what gets drawn.

Five of eight have cleared the 10-hour bar. Three haven't, and Cole hasn't logged anything.

Service hours · new members · Fall 26Your bar · 10 hrs

Above your 75% bar for most of the term, but three of the last four fell under it.

Chapter meetings · attendance · Fall 26Your bar · 75%

Granted when

Two or more rows of one kind, and every row carries a number in one unit (hours, dollars, percent, GPA). Checked before the date forms, so a meeting with a number never loses it to a logbook.

Drawn from

Bars are scaled to the largest value in the answer (percentages to 100), so they can only say what the rows already say. Rows with a date keep date order and get a date stub in place of a rank. The dashed bar appears only if the org set that threshold in Settings; with no threshold there is no cut line and no peach.

On the wire

layout: "ranked"
row: { title, value: "22 hrs",
       num: 22, ref }
bar: { at: 10, label: "Your bar" }
02

Today line

When every row has a date, what matters is which side of today it falls on. Tasks and events share one rail in date order, a rule marks today, and each row says how far away it is. Above the line, only open work is late and looks it. An event that already happened is just earlier, and is drawn quiet.

Nine things, and two are already late. The venue deposit is the one that costs money.

Granted when

Every row is something on the calendar (a task, deadline or event) and at least one is today or later. Tasks and events together are fine: date order is checked before sorting by kind. All in the past is a Logbook.

Drawn from

The date comes from the record behind each row, never from the model's subtitle. Groups are fixed: Before today, Today, Next 7 days, Later. “Late” is never a group and never an event: it is one open task whose due date has passed, marked on its own row. An empty group isn't drawn.

On the wire

layout: "dated"
row: { title, subtitle, ref,
       date: "2026-11-04",
       late?: true }
03

Logbook

“How many have we had?” is a count of things that already happened. The count leads, and the events are shelved under the month they happened in, each as a small dated ticket. Six rows of scrolling become one glance. Only months that had something are shown.

Six so far. Four of them were in October, with one each in September and November.

Granted when

Every row resolves to a dated record and every date is before today, and the rows are events or finished work. Needs nothing but a title and a date. Payments go to the Receipt and late open tasks to Past due.

Drawn from

The count is the number of rows, so it can't disagree with the list. Each ticket is one row and opens the same record a row would. A month with nothing in it isn't drawn. Past about a dozen in one month, the month shows its first tickets and a “+ 9 more”.

On the wire

layout: "logbook"
row: { title, subtitle?,
       date: "2026-10-03", ref }
Same question, any weekThe form comes from what was asked, never from how many came back. One event is a logbook with one ticket, not a different kind of answer.

04

Progress

When every row has a status, the first thing anyone wants is the count. One block per row gives it at a glance. Underneath, the stuck rows come first, and finished work folds into a single line instead of taking up half the answer.

Five of nine done. The venue deposit is late and nobody owns the photographer.

Winter Formal · Dec 5 · 9 tasks

Granted when

Every row has a status from one closed set (the typed enums in lib/state), and at least two different statuses are present.

Drawn from

One block per row, so the strip is a count and not a percentage someone has to trust. “Stuck” is derived: late, or no owner. Hover a block to find its row. Done rows stay in the answer; they're just folded.

On the wire

layout: "status"
row: { title, subtitle,
       status: "done"|"open"|"stuck",
       ref }
05

The record

Some questions ask for one thing: when is the next meeting, who is the treasurer. Handing back a list of one is a strange reply to that, so Ask Chapt shows the record itself, with the facts you would have opened it to see. This is decided by the question. A “how many” or “which ones” that happens to find one result keeps its own form.

Sunday at 7 in the Union. It's mandatory, and the agenda isn't set yet.

SUN15NOV
Meeting · in 5 days

Chapter Meeting

7:00 PM · Student Union 204

MandatoryWeekly
AgendaNot set yet

Last week72% came

Daniel runs the books. Maya can also take payments if he's out.

Granted when

The question was a lookup (“when is the next…”, “who is our…”) and it resolved to one record, or the pair that shares the job. A count or a list that came back short is never turned into cards.

Drawn from

This is the peek sheet's own card, built by peek-service from the database, placed inline. The model writes the verdict and nothing on the card. What a viewer can see on it follows the same permissions as the peek.

On the wire

layout: "record"
row: { title, ref,
       card: PeekCard }
06

Side by side

When each row carries the same few facts, the list crams them into a subtitle and you read six sentences to find one bad number. As columns, the eye runs down each measure, and the cells under your thresholds are the only ones with colour. Tap a heading to sort.

Mostly fine. Two officers are under a bar: Tyler on dues and attendance, Devin on GPA.

Granted when

Two or more rows of the same kind, and the question asked for two to four measures of each. Dated rows qualify too (“how did each party do?”): the first column shows the date and the rows stay in date order.

Drawn from

Each cell is read from the member's roster row. A cell is tinted only against a threshold the org has set; a measure the org doesn't track isn't offered as a column at all. On a phone the name column pins and the measures scroll.

On the wire

layout: "table"
cols: [{ key, label, bar? }]
row: { title, subtitle, ref,
       cells: { gpa: 3.1, … } }
07

Roll call

When the rows are people and the only fact is that they're on the list, eleven boxes is eleven lines of scrolling for eleven names. As a roll, the count leads, the names sit together, and a split that matters (excused or not) is the only structure.

Eleven missed Sunday. Four had an accepted excuse; seven didn't.

Granted when

The rows are members and carry nothing but a name, or a value that takes only two or three distinct forms (which becomes the split). Any number of them: two names or forty draw the same way.

Drawn from

Each chip is a member row and opens the same member card a row would. A short note rides on a chip only when the row had something extra to say (“3rd miss”). There is no size at which it turns back into boxes, so “who missed chapter?” looks the same every week.

On the wire

layout: "roll"
row: { kind: "person", title,
       group: "No excuse",
       value?: "3rd miss", ref }
08

By drawer

Sometimes the rows really are different kinds of thing: an event, two tasks, a payment, a doc. That's where the list belongs, with one fix. Rows are filed under the part of the app they live in, and each kind puts its own key fact on the right.

Five things in four places. The retreat is Nov 21, the cabin deposit is paid, and waivers still need an owner.

Granted when

The rows resolve to two or more kinds of record and they aren't all things on the calendar (tasks and events together go on the Today line). Drawers appear in the sidebar's order, and a drawer the org has switched off never shows.

Drawn from

Nothing new is needed: the grouping is the record type the server already attaches to each row. The tab colours are the app's own section colours.

On the wire

layout: "drawers"
row: { title, subtitle, value,
       ref: { type, id } }
09

Receipt

When every row is a payment, the rows are only half the answer; the other half is what they add up to. The figure asked for leads, each entry is a line with its amount in one column, and the lines visibly sum at the bottom. Money in and money out are told apart by sign and colour, never mixed into one number without saying so.

$1,228.40 so far, in four payments. Ticket sales have already covered it.

Winter Formal · paid out so far
$1,228.40
+ $21.60 after ticket sales

Granted when

Every row resolves to a ledger transaction. Checked before the Logbook, because payments are dated and in the past too.

Drawn from

Amounts come from the ledger rows; the totals are summed by the server from exactly the lines shown, so the receipt can't disagree with itself. “Pending” is the reimbursement's real state. If the answer is a sample of a longer list, the total line says “of 6 shown” and no net is drawn.

On the wire

layout: "receipt"
row: { title, subtitle, ref,
       date, cents: -18640,
       pending?: true }
totals: { out, in, net }
10

Past due

Late work isn't history, so it doesn't belong in a logbook. What matters is how late and who has it. Every bar ends at the same edge, today, and reaches back to the day the task was due, so the longest bar is the oldest problem. The owner's face is on the row; a task nobody owns says so.

Five things. Insurance is 18 days late, Marcus has two, and one has no owner.

Open and past due · 5LateOver two weeks

Granted when

Every row is an open task or deadline whose due date has passed. One row that is done, or due later, and the answer is Progress or the Today line instead.

Drawn from

Bar length is today minus the due date, nothing else. The scale is whole weeks, rounded up from the oldest row, so one very old task doesn't flatten the rest into slivers: past eight weeks the bar is capped and its label carries the real number.

On the wire

layout: "pastdue"
row: { title, ref,
       date: "2026-10-23",
       owner?: { name, id } }
11

Game plan

Advice rows are ranked, but in boxes the first suggestion looks exactly as important as the sixth, with a small “high” or “later” in the corner. Here the ranking is the layout: what to do first gets a card and room to say why, the next tier is a plain row, and the someday ideas are a quiet line each. Every item still says where it takes you.

Start with the two that cost nothing: make the meetings count, and close the late-excuse gap.

Granted when

Every row carries a tier. That is already how advisory answers arrive, so nothing changes on the wire; this is the same answer drawn differently.

Drawn from

The three bands are the three tiers the server already validates (a tier can never improve further down the list). The pill on each item is the row's existing action: an arrow goes to a screen from the closed list, a dashed plus drafts an event for approval. At most two cards; a third “high” row joins them as a full-width card.

On the wire

layout: "plan"
row: { title, subtitle,
       tier: "high"|"medium"|"later",
       screen: { label, path } }
12

Nothing yet

“None” on its own leaves a doubt: is it really zero, or did it not find them? So a zero answer is one empty slot: a blank calendar page, exactly what there are none of, and a line saying what was checked. Under it, what those things were filed as instead, so if the chapter calls its service events “Philanthropy” the reader sees that at once and one tap re-asks.

None filed as Service this term. Six are filed as Philanthropy, if that's what you mean.

No events filed as Service this termChecked all 41 events since Aug 24
The 41 are filed as

Granted when

The question was a count or a list, the tools ran cleanly, the word asked about matched a real category or status in this org, and nothing was in it. If the word matches nothing the org uses, Ask Chapt asks which one was meant and never claims a zero.

Drawn from

The slot states the filter in the org's own word (“filed as Service”), not a paraphrase. The strip below is a plain count of the same 41 records by category, straight from the tool result; nothing is guessed to be similar. One chip is outlined only when its name is a known alias of the word asked.

On the wire

layout: "zero", rows: []
searched: { count: 41, label,
            filter: "Service" }
instead: [{ label, count,
            likely? }]
13

Yes or no

“Has all of exec paid?” wants one word, and then only the part that makes it a no. So the word is stamped. Beside it, everyone the question covered is one small face, with the exceptions ringed. Below, the exceptions are the only rows. The people who are fine fold into a single line, and a clean yes has no rows at all.

Not yet. Tyler still owes $380; the other five are paid up.

Yes, all eight.

No, and it was due six days ago.

NoThe deposit hasn't been paidIt's Marcus's task, still open

Granted when

The question is yes-or-no, and the server can mark every row it covers as passing or failing a test it can run (owes nothing, task done, attended). Checked first, before any other form.

Drawn from

The stamp is computed, never written: Yes only if every row passes, No if any fails. The model writes the sentence but cannot choose the word. If even one row can't be judged (a new member with nothing recorded yet), there is no stamp and the answer falls through to its ordinary form, with that row marked “not measured”.

The three cases

No, with exceptions: the failing rows are listed and the rest fold. Yes: faces only, no rows. One thing (“is the deposit paid?”): the stamp and that one record as its evidence.

On the wire

layout: "yesno"
holds: false
row: { title, value, ref,
       pass: false }
→

How a form gets chosen

The model can ask for a layout, but the server only grants it when every row qualifies, checked in this order. The first match wins. Three things hold the order together: a number on every row is drawn before a date is; a shared date is used before rows are sorted by kind; and no step looks at how many rows came back, so the same question gets the same form every week. If nothing matches, or a single row is missing what the form needs, the answer is drawn as the list it is today, so a wrong guess costs nothing.
