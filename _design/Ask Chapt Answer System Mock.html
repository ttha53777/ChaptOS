Ask Chapt · answer system

No answer should look like a fallback.

The list forms got the hard cases right: a sentence that judges, one drawing on a sheet, then where it came from and what to ask next. Everything without a shape still drops to a bare sentence or a column of prose. This page turns what the shapes already do into rules every answer follows, and adds eight blocks so nothing falls through. Flip Today / New on any answer to see the same turn both ways.

The system

Every answer has three parts in the same order. The shapes you already have are bodies, and the new blocks are bodies too. Nothing else changes: same ledger, same trace, same writ.

Five of nine done. The deposit is late.

One body block, always on a sheet

FootingWhere it came from, was it useful, what to ask next.
Stopped, failed, drafted: a slip replaces the body.
SlipStatus is never prose.
Prose never stands alone.

Every answer gets a body block. MarkdownLite stays only as the streaming state, while text is still arriving. When the answer settles it becomes a Note or a block.

One mark, and its color means something.

The headline's highlight takes the answer's tone. Mint is good, peach needs attention, butter is now or neutral, sky is your own record, lilac is Chapt itself. The block's accents use the same tone.

The model picks the words. The server fills the facts.

The same rule as sources and shapes: every number, date, name and quote in a block is read back from tool results that ran this turn. The model names the block type and writes the sentence.

Anything named can be opened.

A person, event, task or transaction mentioned in running text becomes an entity chip that opens the same peek a row does. Matched server-side through RefIndex, never from model markup.

Rows always ride along.

Every block still ships plain rows (or a plain verdict), so older native builds that ignore the new field draw what they draw today. Purely additive.

Figure

When the answer is one number, draw the number. It comes with its direction since a date you'd care about, a sparkline only when the history is real, and a "how it's counted" strip whose terms add up to the figure. Each term opens the ledger lines behind it.

Granted when

The question asks for one quantity (a balance, a count, an average, a total) and a figure tool ran this turn: balance, roster count, budget remaining, attendance average.

Drawn from

The number, delta and terms all come from the tool result. The terms must add up to the figure or the strip is dropped. The sparkline only draws when there are at least four real points. A count gets a split instead, only from fields that exist (joined date, role, exempt), and the boxes must also add up.

Second turn shows

The member count used to take the fast path straight into prose. Same figure, same sheet, whichever path served it.

On the wire

shape: { type: "figure",
  metric: "balance" }
// server fills:
value, unit, delta?: {by, since},
series?: [..], terms?: [{label,
  amount, op, ref}]

Fact card

"When is it", "where is it", "who's running it": the question is about one record, so the answer is that record as a ticket. The date stub sits where your eye starts, the facts sit in a grid, and the button that opens it sits where a row's chevron would have been.

Granted when

The answer resolves to exactly one record (an event, task, member or transaction) and the question asked about its details. The list forms' Record is the same idea for a list of one. This is its sibling for "tell me about X".

Drawn from

The record's own fields, read back through the peek builder that already powers row sheets (PeekCard), so the ticket and the sheet can't disagree. Facts with no value are left out instead of showing a dash. Time and place are the event's own fields, the owner is its Programming owner, and spend is the sum of transactions linked to it. The second button is an ordinary follow-up.

On the wire

shape: { type: "card" }
rows: [{ ref: {type:"event",id} }]
// server fills from PeekCard:
card: PeekCard { title, badge?,
  facts[], sections[] }
03

Steps

A how-to is a route. The breadcrumb shows where it lives in keycap pills, the steps hang off a rail, and the fields you'll be asked for show as dashed slots, so the screen looks familiar when you get there. It ends with the button that takes you there.

You can do this under Settings → Custom Metrics:

  1. Click Add metric.
  2. Give it a name (e.g. "Study hours"), a unit, and a goal.
  3. Optionally set an at-risk threshold.
  4. Save. It will show up on the roster and member cards.

Add it as a custom metric in Settings. It takes about a minute.

Settings Custom metrics Add metric
  1. Name it

    The slug can't be changed later. Unit is optional.

    NameStudy hoursSlugstudy-hoursUnithrs
  2. Set the goal per member

    At or above it counts as on track.

    Goal (per member)20
  3. Draw the at-risk line

    Under it counts as at risk. Watch is an optional middle band.

    At Risk below8Watch below12
You'll need Manage settings. You have it.

Granted when

A product how-to whose path is in a closed HOWTO playbook (like SCREEN_PATHS). That covers single-step answers too, which today stay plain text. A how-to with no playbook entry becomes a Note with a Go-to strip.

Drawn from

The crumbs, steps and field labels come from the playbook, written against the real form (Name, Slug, Unit, Goal, At Risk below, Watch below), so they match the screen. The model only picks the playbook and may fill the example values ("Study hours") from the question. The permission line is checked against the asker's role (custom metrics need MANAGE_SETTINGS), like the writ's gate.

On the wire

shape: { type: "steps",
  playbook: "custom_metric",
  examples?: { name: "Study hours" } }
// server fills: crumbs[], steps[],
screen, perm: {ok, label}

Reasons

A "why" is a judgment the reader wants to check, so the answer opens the case file. The folder draws the evidence once: the bar he's under, every mandatory meeting this term, and the rest of his record. Each reason is an index card, and touching it lights up the part of the folder it rests on. What was ruled out is stamped, and the way back is worked out from the calendar, not guessed.

Granted when

A "why" about a judgment the app made (at risk, flagged, over budget, late) when the tools that hold the evidence ran this turn. The folder's panels depend on the judgment: attendance draws the gauge plus the meeting strip; GPA, service or a custom metric draws the gauge alone, since those have no per-event history.

Drawn from

The folder is built by the server from the reads: the gauge from the member's metric and the org's threshold, the strip from every mandatory meeting in the term (attendance records, excuses, and the ones still scheduled), and the rest of his record from his roster row against your Settings thresholds. Draft a check-in task is the existing add-deadline proposal, assigned to whoever you pick. The model writes up to four reason cards and tags each with the panel it rests on. A tag that doesn't match a panel drops the link, not the card.

Fair and the way back

Both are computed, never written. An excused row carries the officer who decided it and the reason the member gave. "Not counted" lists the rows the metric excluded. "The way back" counts the scheduled meetings left and works out the outcomes: all of them, and one missed. If no number of meetings would clear the bar, it says so plainly.

On the wire

shape: { type: "reasons",
  subject: {type:"member",id} }
reasons: [{ title, body, refs,
  panel: "gauge"|"strip"|"rest" }]
// server fills: case{gauge,
strip[], rest[], excluded[],
pathBack[{label,pct,clears}]}

Quote

When the answer is what someone wrote down, show what they wrote. The minutes passage goes on a legal-pad strip with its meeting and date, the decision is stamped, and that meeting's action items show underneath, ready to tick off.

The chapter approved $3,000 for Winter Formal at the Oct 20 meeting.

You approved $3,000 on Oct 20. The $800 deposit was due two days ago and isn't marked done.

Granted when

The answer rests on a passage from search_meeting_notes or an attached file. Quoted text is copied verbatim from the snippet by index, never retyped by the model.

Drawn from

The snippet, meeting and date come from the minutes record. The Decided stamp appears only when the passage matches one of the meeting's summarized decisions. Decisions are plain text with no vote counts, so no tally is drawn. The action items are the meeting's notesSummaryData items, and ticking one uses the existing tick-off route. File quotes use the same strip with the file name and page in the header.

On the wire

shape: { type: "quote",
  snippet: 0 }
// server fills: source{meeting,
date}, text, decided: bool,
items[{title, owner, done, due}]
06

Note

The catch-all, done properly. Prose sits on a notebook margin rule, headings shrink to kickers, bullets become tone diamonds, UI labels become keycaps, and any record named becomes a chip. It closes with a tip if there is one, and the screens it mentioned as places to go.

How attendance works

ChaptOS tracks attendance for mandatory events.

  • Taking it: officers can mark who attended after the event, or open a live check-in during it.
  • Excuses: members submit an excuse and officers review it.
  • Exemptions: a member can be marked exempt for a whole semester.

The at-risk line is set under Settings → Thresholds. Right now 3 members are under it.

Only mandatory events count, and an approved excuse takes that meeting out of the math.

Taking it

  • During the meeting, Open check-in and members check themselves in.
  • Afterward, Mark who attended from the event.

Excuses and exemptions

Members file their own Excuse, before or after the meeting, and an officer reviews it. Someone away all term (abroad, co-op) gets Mark exempt… instead, which takes them out of every mandatory event that semester.

CBCole DADev MLMaya are under your 75% at-risk line.

Tip: the at-risk and watch lines live in Settings › Thresholds, next to the GPA and service ones.

Granted when

Nothing else matched. This is the only place prose is allowed to be the body, and it's still a block.

Drawn from

Same markdown subset as today, typeset differently: ### becomes a kicker, - becomes a diamond, and `Label` becomes a keycap. Names become chips only when the server matched them to a record this turn (RefIndex). Unmatched names stay text. Keycaps are only allowed for labels that exist in the UI (a closed list, like the screen keys). The Go-to strip comes from screen keys, the same closed enum advisory rows use.

While it streams

Text arriving token by token still renders as today's .note with the caret. On the final event it swaps to the Note in place, with no layout jump because the type sizes match.

On the wire

shape: { type: "note" }
note: { md, refs: [{text, ref}],
  tip?, screens?: ["settings","events"] }

Clarify

Today a clarifying question is one line of prose, and you type the answer. The new version draws each choice as a tile showing what you'd get back, so picking one is a tap. A dashed "something else" goes to the composer.

Could you clarify what you'd like to know about last semester? For example, attendance, dues collection, or service hours?

Happy to. Which part of Spring 26?

Granted when

A clarifying question with two to four answers that each map to a known area. Today these are "one-line clarifying questions" in plain text. They go through compose_answer as an askback with areas instead.

Drawn from

Each tile's icon, color, line and sketch come from a closed area list (attendance, money, service, tasks, events, roster). The sketch is a fixed glyph, not data, so it promises nothing it hasn't read. A tap sends the chip text, exactly as an askback chip does today. It's the same block as Which-one's people cards, for topics instead of people.

On the wire

askback.questions[0]:
{ question, chips: ["Attendance",
  "Money","Service"],
  areas: ["attendance","money",
  "service"] }
08

Decline

Out-of-scope shouldn't sound like an error. A quiet dashed slip says what Chapt can see and why this isn't in it, then offers the closest questions it can answer about the same thing.

Sorry, I can only help with questions about your chapter's data in ChaptOS. I don't have access to weather information.

I can't see the weather, but the cookout is Saturday at 1 PM.

Outside what I can read

I only read Sigma's records in ChaptOS (events, money, people, minutes, docs). A weather app will know better.

Granted when

The out-of-scope refusal path. If the question names something Chapt can read (the cookout), it answers that part in the headline first, the same "answer what you can, then ask" rule askback follows.

Drawn from

The scope line is fixed copy plus the org's name, and the model can't reword it. The two follow-ups are ordinary follows, shown inside the slip because there is no other body.

On the wire

shape: { type: "decline" }
verdict, follows[]
// no rows, no sources

Granted when

Client-side only. Every case is already known to ChatWidget: a proposal with no answer body, stopped: true, and the stream's catch branch that writes "(network error)" today.

Drawn from

Stopped keeps the ledger steps that did finish (they're on the message) and strikes through the rest. "Finish it" re-sends the same question. "Nothing was changed" is always true here, because writes only happen on Approve.

How it would ship

Cheapest and most visible first. Phase 1 changes no wire and touches every answer. Each later phase is one family of shape types, behind the same pattern as list forms: a model-named type, a server builder, a client sheet, and rows always kept.

Phase 1 · client onlyThe grammar
  • Footing replaces meta-row + follows
  • Tone classes on every answer
  • Slips for drafted, stopped, network error
  • MarkdownLite restyled as Note (kickers, diamonds, keycaps)
wire: none · ChatMessage.error
Phase 2 · numbersFigure + Fact card
  • figure builder off balance, roster, budget, attendance avg
  • card builder reuses PeekCard
  • Fast-path answers draw them too
shape: figure | card
Phase 3 · plain-text pathsSteps, Clarify, Decline
  • HOWTO playbook enum (crumbs, steps, fields, perm)
  • askback.areas for clarify tiles
  • Refusals + single how-to move into compose_answer
shape: steps | decline · askback.areas
Phase 4 · evidenceReasons, Quote, chips
  • Entity chips via RefIndex in Note + Reasons
  • Quote from minutes snippets + summary items
  • Evals: verbatim quote check, ref resolution
shape: reasons | quote · note.refs
